# SQLite 接管与旧数据迁移边界

## 背景

桌面端原件已落盘，但素材仍读 IndexedDB，标签和坐标仍在全局 localStorage；SQLite 仅供人工核对。切库无法隔离这些状态，旧删除还会物理清理浏览器记录与原件。

## 选项

1. 长期双写两套主库，依赖核对修复差异。
2. 直接切换后删除旧存储，失败时依靠恢复备份。
3. SQLite 成为唯一元数据主库，旧存储只作迁移源与保留备份，缩略图单独作为派生缓存。

## 决定

采用选项 3，落实产品方案既定的 SQLite 架构：

- 桌面存取显式绑定库根目录，后端校验当前根目录，拒绝过期请求；切库等待未完成写入并重建页面状态。
- 迁移先复制并核对原件，再将素材、标签、旧状态和完成标记放入一个 SQLite 事务；失败不提交标记，重试不复活墓碑，保留旧数据。
- 无归属缓存不自动复制到空库。自动迁移需与已有影子库哈希匹配，或由用户在设置中明确指定迁移目标；同一来源只认领一个库。
- 删除只写库内递增 deleted_seq；可见性在视图中求值，标签、原件与画布坐标不级联清理。恢复沿用原 id；新素材使用 UUIDv7。
- 画布与视口暂以库内 JSON 状态保存，后续再按收藏集/画板模型拆表；缩略图缓存可丢弃并从原件重建，不参与元数据双写。
- 配置写入经非 C 盘校验的位置，旧 AppData 配置只读兼容。测试单独指定非 C 盘 WebView2 用户目录，避免改变用户已有浏览器数据来源。

## 代价

旧备份暂占空间，尚不执行永久删除或 GC；缓存丢失后的预览需要重建；分页、完整画板关系及 Rust 图像管线仍是后续工作。跨库迁移界面、配置与 WebView2 用户目录的自动搬迁不在本次范围，避免自动搬迁使旧 IndexedDB 来源不可见。
