# ADR 0007：取消体积预算，体积只作记录

日期：2026-10-29。状态：已生效。

## 背景

05 §5 曾把「前端新增依赖合计 ≤ 125KB gzip；安装包 ≤ 35MB（方案 R）」写成硬约束，02 §7 配了一张同名预算表。
实际执行时暴露两个问题：

1. **口径不清**：125KB 说的是"新增依赖"，但唯一能被 `pnpm build` 量到的是总量。当前产物 476.75KB
   （gzip 155KB）里绝大部分是应用自身代码，无法用这条预算判断"这次改动是否超了"。
2. **它开始反向干扰选择**：为了守住一个没有基线的数字，讨论一个能力库时会先问"多大"，
   而不是"它是不是该由我们自己做、维护成本多少"。当前阶段（工程验证、单机自用、尚未分发）
   体积不是真实风险。

## 选项

1. 保留预算，补齐口径（区分增量与总量）与测量方式，继续当验收项。
2. 取消体积门槛，产物体积只记录、只观察趋势。
3. 只取消前端 gzip 预算，保留安装包 35MB。

## 决定

采用选项 2。

- 05 §5 删掉体积预算，改为「不设门槛」；依赖取舍仍要回答 §5 的四个问题，但第三问从"体积代价"
  改成"替代方案与更简单做法"，体积不再是可否决一项依赖的理由。
- 02 §7 的表改成「体积参考（不作门槛）」，保留数值是为了回答"某个改动让产物涨了多少"。
- 00 §7.3 里原本用体积论证方案 R 的句子已改写：方案 R 仍成立，但理由换成单一解码管线、
  无跨语言边界、内存与启动占优；00 §10 验收表里"安装包 ≤ 35MB"改成"记录实测值，不设门槛"。
- 构建产物大小继续在交付说明与 `pnpm build` 输出里记录实测值。

## 代价与边界

- 失去"依赖膨胀"的硬闸，改由 review 判断。当前由单人 + AI 协作，可接受；团队扩大后可能需要
  重新引入，但必须同时给出基线口径与测量方式。
- **两条与体积无关的约束继续保留**，不要因为本 ADR 一起丢掉：
  1. CJS 单文件包必须构建期提取（`akar-icons` 即此类）。理由不是省体积，而是避免整包死代码进产物、
     拖慢启动与热更新（见 `docs/03` §6.1 的实测 +340KB）。
  2. 搜索的中文切分规则必须与数据库索引共用一套（bigram），保证本地与云端命中一致。
- 若将来面向公网分发、增加 Web 端或做安装包体积敏感的分发渠道，可重新引入预算；
  届时先定义"量什么、怎么量"，再定数字。
