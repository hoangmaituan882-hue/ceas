## 0. 为什么先做采集

产品能不能被每天打开，取决于三段闭环：**进来 → 出去 → 信得过**。当前三段各缺一块，
而"进来"是唯一决定留存的前置：用户的实际动作是「截图 → 存 → 继续画」，
中间每多一次切窗口，就多一批躺在桌面上的截图。

本文件先覆盖"进来"，把 Pixcall 已验证的三条入口逐条对齐；"出去"与"信得过"列在后面，
属于同一阶段必须补齐的门槛，不是可选项。

## 1. 三条采集入口（对齐 Pixcall，不照抄实现）

| # | 入口 | Pixcall 的行为 | Ceas 现状 | 差距 |
| --- | --- | --- | --- | --- |
| 一 | 拖 / 粘贴到主窗口 | 拖到文件列表 → 入根或收件箱；拖到左侧文件夹 → 入该收藏集；文件夹保留层级 | 已接原生路径拖放、当前位置/侧栏落点、文件夹层级与空集、资源管理器文件粘贴 | 资源管理器实际手势人工补验、截图位图粘贴、超大目录准备进度 |
| 二 | 拖 / 粘贴到资源管理器里的库文件夹 | 文件量大时比拖窗口更快（系统自己拷，应用只索引） | **已具备**：监听 + 核对（两次 750ms 观察 → 先核对收藏集、再核对文件 → 只哈希变化的文件） | 大批量的进度/暂停粒度、扫描是全量而非增量、读盘竞争 |
| 三 | 拖到托盘常驻图标 | 存入库根目录 | 无托盘 | 托盘、关闭到托盘、单实例锁 |

**方法二是本产品的结构性优势，不是补丁。** 因为库就是普通文件夹（ADR 0002），
用户可以在资源管理器里用任何方式拷入、解压、同步盘落地，Ceas 只负责把事实读进来。
Pixcall 需要专门说明"这种方式更快"，对 Ceas 而言这是默认路径 —— 但它对实现有三条硬要求：

1. **不许把复制中的半成品入库**：两次观察稳定（大小 + 纳秒修改时间）才索引，仍在变化的留给下一轮。
2. **收藏集必须先于素材核对**：新目录要先成为收藏集，素材才有所属；顺序反了会把素材记成"无归属"。
3. **大批量时不能只靠"每 2 秒全量扫描"**：一万文件的全量扫描是纯读盘成本，
   要么加增量（记录目录修改时间/通知合并），要么在批量期间降频并给出明确进度。

## 2. 落点与共同规则（三条入口必须一致）

### 2.1 目标由"你现在在哪"决定（已定）

拖到窗口的落点不是固定的，而是取当前导航位置。这样用户不用先想"我该拖到哪"，只需要已经在正确的地方。

| 当前位置 | 拖入文件 | 拖入文件夹 |
| --- | --- | --- |
| 全部素材 | 收件箱（库根） | **进库根，保留层级**；顶层目录成为收藏集 |
| 某个收藏集 | 该收藏集目录 | 进该收藏集，保留子目录层级（子目录成为子收藏集） |
| 标签 / 搜索 / 筛选结果 | 收件箱 | 进库根，保留层级 |
| 回收站 | 不接收（整块显示"回收站不能导入"） | 同左 |
| 托盘图标 / 直接放进库目录 | 库根 | 按实际目录归属 |

拖到侧栏某个收藏集上时，以**被拖到的那个收藏集**为准，覆盖当前位置。

**文件夹永远保留层级，任何位置都不摊平。** 理由有三条，而且互相独立：

1. 摊平会撞名 —— `海报/a.png` 与 `海报/b.png` 落到同一层，只能变成 `a (1).png`，用户认不出哪个是哪个。
2. 摊平会毁掉用户已经做好的分类，而分类正是他来这个软件的理由。
3. 收藏集就是文件夹。把文件夹摊平，等于在这套模型里开了一个"你能拖进来，但结构不算数"的口子。

所以"拖文件夹到全部素材"的结果是：**顶层目录成为收藏集，内容进那个收藏集，收件箱不增加** ——
文件夹本身就带着归属信息，不该被当成一堆散图。只有拖**单个文件**时，它没有归属，才进收件箱。


### 2.1.1 实现岔路：拿路径还是拿 File

"保留层级"这条要求会改变拖放的技术选型，开工前必须先定：

| 方案 | 能拿到什么 | 代价 |
| --- | --- | --- |
| HTML5 拖放（现状） | `DataTransfer.files` 里文件夹是**空 File**，没有层级；要结构必须用 `webkitGetAsEntry()` 自行递归 | 递归 + 逐文件读入，边界（超大目录、符号链接、权限）要自己处理 |
| Tauri 原生拖放 | 直接给**磁盘路径**，文件夹天然有层级 | 需把 `dragDropEnabled` 改回 `true`；设置后 HTML5 的 drop 收不到事件（当初正是为了解决这个才关掉的） |

**已采用 Tauri 原生拖放**（ADR 0009）。理由是它与现有链路天然对齐 —— `importSources` 已经支持
`{ path }`（磁盘读取，Pixcall 导入就是这么走的）与 `relativePath`（保留目录），
也就是说"拿到路径"之后剩下的事代码里都有；而 HTML5 路线要在前端重新实现一遍目录遍历。

需要注意的副作用：关掉 HTML5 拖放后，**应用内**基于 HTML5 的拖放也会失效（目前没用它做格内拖动，
用的是 Pointer Events），所以影响面只有"从系统拖入"，而这正是要替换的那条。

### 2.2 其余共同规则

| 规则 | 约定 |
| --- | --- |
| 收件箱 | 只有"没有目录归属"的素材算收件箱；带目录的导入不算（否则收件箱永远清不空） |
| 同名冲突 | 从不覆盖：生成 `名称 (1).ext`，并在结果里说明保留双方 |
| 复制中 | 未稳定不入库，不报错；稳定后自动进入 |
| 不可预览的类型 | 仍然入库为 `file` 类型，显示信息并可在资源管理器定位 |
| 失败 | 进"文件核对"面板，可重试、可定位，不伪报整批成功 |
| 大批量是无感的 | 不弹模态、不抢焦点、不要求先点"开始"；进度只出现在顶部状态行，完成给一次轻提示。**不提供"暂停核对"开关** —— 用户不该为了拷文件去理解应用的扫描机制 |

## 3. 验收（每条入口都要能跑出来）

**方法一**

- 在「全部素材」下拖 3 个文件 → 收件箱 +3，网格可见，双击可看大图。
- 在「全部素材」下拖一个含子目录的文件夹 → 顶层目录成为收藏集（含子集），**收件箱计数不变**，层级完整。
- 在某个收藏集内拖同一个文件夹 → 进该收藏集，子目录成为子收藏集，**层级不丢**。
- 在标签 / 搜索结果下拖文件 → 进收件箱（标签是属性，不是位置，不能"拖进标签"）。
- 在回收站下拖任何东西 → 整块拒绝并说明原因。
- 拖 2 个文件到侧栏某个收藏集上 → 进该收藏集，覆盖当前位置。
- 资源管理器复制 3 个文件，回窗口 `Ctrl+V` → 与拖入等价（含上述位置规则）。

**方法二**

- 往库目录拷 500 张 → 不做任何操作，2–5 秒内网格出现并逐步补全缩略图。
- 拷 3000 张 → **全程无模态、无焦点抢占、无"开始"按钮**；顶部状态行显示正在核对；
  完成后一次轻提示「已新增 N 项」。期间滚动网格、打开详情都不卡。
- 拷一个 2GB 视频 → 复制过程中不入库，复制完自动入库并可播放。
- 拷贝过程中在外部删掉其中一个文件 → 该条不出现，其余正常；不报"整批失败"。

**方法三**

- 托盘图标**默认常驻**（设置里可改为关闭即退出，但退出必须是显式菜单项，不能靠点 × ）。
- 拖 3 个文件到图标上 → 进库根；应用未运行时自动启动并完成导入。
- 关闭主窗口 → 收进托盘；单实例：再次启动聚焦已有窗口。

## 4. 出去（同阶段必做）

现在库是"只进不出"，而存图的唯一目的是用。四项，按价值排序：

1. **拖出到其它应用**：Windows `DoDragDrop` 带真实文件路径，可拖进 Figma / PS / 聊天窗口。
2. **复制**：复制原图（位图）、复制文件路径。
3. **导出**：选中项复制到指定目录（保留原名与目录），可选打包 ZIP。
4. **在资源管理器中定位**：已有 `reveal_in_explorer`，接到右键菜单与详情。

验收：从 Ceas 拖一张图到 Photoshop 打开、拖一张到微信发送、导出 20 张到指定目录且同名不覆盖。

## 5. 删除闭环的四个缺口（跟随 Pixcall 后必须补）

> **落地状态（2026-10-29 晚）**：
> §5.1 彻底删除/清空 **已实现**；§5.2 磁盘删除项 **已实现**（语义改为"合并整理信息"，见正文）；
> §5.3 目录级汇总与「重新定位」**已实现**（重新定位 = 把库外目录收回库内原位置，见正文）；
> §5.4 内容修改 **已收口**（`decode` 状态 + 失败分类 + 「按普通文件保留」+ 两侧测试）。

外部删除已改为跟随进回收站（[ADR 0008](adr/0008-follow-external-delete.md)）。这条改动一旦落地，
下面三处会立刻变成每天都会撞上的裂缝 —— **不是"以后再做"，是同一批活**。

### 5.1 彻底删除与清空回收站（已实现）

**现状**：回收站视图里 `BatchBar` 只是把「删除」换成「恢复」，全仓搜 `purge` / `empty_trash` / `permanent` 零命中。
用户删掉 20 GB 素材，磁盘空间一点没变 —— 他会认为软件在骗他。

**要做**：单条「彻底删除…」+「清空回收站…」；确认框写明项数与释放体积；先删回收区文件再提交记录删除。

**验收**：

- 回收站删 12 项（1.8 GB）→ `.ceas/trash` 少 12 个文件、磁盘可用空间确实增加、记录消失；
- 对「磁盘删除」项执行彻底删除 → 不报错，释放体积显示 **0**（没有原件可删）；
- 中途失败 → 不报成功，状态可解释、可重试；
- 存在未完成的恢复任务指向该项 → 按钮禁用并说明原因。

### 5.2 「磁盘删除」项的恢复路径（部分实现）

**现状**：这类项进了回收站，但**没有可还原的字节**。现有 `TrashRestore` 预览会因"回收原件暂不可用"
把恢复按钮禁用 —— 等于把一个死胡同摆给用户。

**做成什么样（已实现，与最初设想不同）**：原计划是"重新指认到库内某个文件"，实现时否掉了 ——
原件已经不存在，内容哈希不可能对上；硬指过去等于让用户以为字节回来了。

改成**整理信息搬家**：`merge_into(source, target)` 把标签取并集、描述/来源/评分只在目标为空时补上、
`created_at` 取更早的，然后删掉原记录（回收区里的原件一并清除）。用户的心智是"这张我还有另一版"，
不是"文件复活了"。面板文案也据此改了：说明没有原件，给**合并**与**清记录**两条出路，
另加一条"把文件放回原处会自动复活"。

**验收**：

- 在资源管理器删一张 → 回收站出现该条且标「磁盘删除」→ 点恢复 → 出现重新指认面板，不是原来那套预览；
- 原文件放回原处 → **复活原记录**（标签、描述、评分回来），不新增一条重复素材；
- 重新指认到另一份内容一致的文件 → 关联成功，原条目恢复可见。

### 5.3 目录级消失的汇总（已实现）

**现状**：整目录被外部删掉，会变成 N 条单项 `missing`；收藏集本身知道自己是 `missing`，
但这个事实没有升到"能一次处理一层"的层级。

**做成什么样**：核对后若一次消失的条目全部属于同一个收藏集，合并成一条汇总（含该收藏集 id），
给两个动作：

```
收藏集「参考」在磁盘上已不存在（80 个文件）
[移入回收站]  [重新定位…]
```

**「重新定位…」的实现语义（与最初设想不同，已按事实修正）**：
原以为可以"改一下数据库里的路径"，但库就是普通文件夹（ADR 0002），收藏集的路径不是标签，
必须是库内真实目录。所以真正的动作是**把那个目录收回库内**：选它现在所在的文件夹，
后端 `collection_recover::relocate` 把它搬回原来的位置。

- 同盘：`fs::rename`，瞬时、不产生第二份；
- 跨盘：逐文件复制 + 双向完整 SHA-256 校验，**原目录保留**，结果里说明"已复制 N 个文件，原目录仍保留"；
- 收回后不碰记录：条目路径没变，核对按"同路径 + 同哈希"把每条复活，标签/描述/评分原样在；
- 拒绝的四种情况各有明确原因：目录还在（`ready`/`unreadable`）、所选是库内目录、所选是资料库根、所选是库的上级目录。

**验收**：

- 删掉含 80 个文件的目录 → 出现 **1 条**汇总，不是 80 条；
- 点「移入回收站」→ 80 项进回收站、收藏集变 `missing`、主网格不再显示；
- 把该目录搬到桌面 → 点「重新定位…」选它 → 同盘瞬时回位、文件数如实回报、条目恢复可见且整理信息不变；
- 批量阈值（>20 项或 > 可见 10%）与 ADR 0008 的确认共用同一套判断，不出现"两个闸门各拦一次"。

### 5.4 内容修改：三处已收口（已实现）

**更正（2026-10-29 晚，我上一版说错了）**：先前我只看 `planFileReconciliation` 的输出
（`matches` 里带 `content_hash` + 一条同路径 `import`），据此判断"会新建一条空素材"。
继续读 `importer.run` 后发现它有更新分支：核对导入带 `options.diskPaths`，
`previous` 按路径命中旧行时**不置空**，`id` 复用旧 id，`progress.updated++`。
落盘走 `copy_verified`，源与目标同一路径时 `copy_file` 直接返回原路径、不复制。
所以**端到端是原地更新**，标签也由 `state.tags[previous.id]` 合并保留。

真正的三处缺口，与现在的处理：

1. **中间态会被看到** → `pending` 只作为一次核对的内部过程存在，同一趟里就会被结算：
   成功变 `ready`，失败按原因落成 `decode` 或留在 `pending`。面板不会再刷出 200 条
   "内容更新尚未完成"——它只在**这一趟没被结算掉**（例如用户取消）时出现。
2. **解码失败永久卡住** → 新增记录状态 `decode`（"字节读到了，但内容解不开"），
   与 `pending`（过程）、`unreadable`（读不到）区分。失败原因由 `classifyImportFailure`
   收成五类（解码 / 权限 / 空间 / 已不在 / 未知），每条给一句话说明 + 建议动作。
   `decode` 的条目在核对里被**两边摘出**（既不判缺失、也不重复导入），直到文件再次变化；
   面板给「按普通文件保留」（`accept_content`：哈希重算、类型降级为 `file`、记录转 `ready`）
   与「忽略此文件」两个出口。
3. **零测试覆盖** → 计划层断言"同路径同身份哈希变 → 复用原 id、原地导入一条"；
   存储层断言"`apply` 后仍是一条记录、`mark_state(decode)`、`accept_content` 后哈希与记录都是新的、
   再点一次幂等"；失败分类另有 3 条 TS 测试。

**验收**：

- 在画图里改一张图并保存 → 网格里仍是 1 项，缩略图/尺寸更新，标签不变，回收站无新增；
- 把某张图改成无法解码的字节 → 该条给出「内容无法解码」+「按普通文件保留」/「忽略此文件」，
  **不**卡成反复重试；点保留后哈希与大小按磁盘重算，类型变普通文件，整理信息不动；
- 批量改 200 张 → 过程中问题面板不刷出 200 条 `pending`；
- `scripts/file-reconcile.test.mjs` 有断言锁定"不新建"。

**为什么排在这里**：四处都改核对与回收的核心，与采集入口抢同一块代码。先做删除闭环，
后面接采集时 `file_reconcile` 只改一次。

## 6. 信得过（商业化的四件"无聊事"）

不属于功能，但缺一件都不能对外分发：

- 代码签名（否则 SmartScreen 拦，第一印象是"有毒"）
- 自动更新（Tauri updater + 私钥三处备份，丢了就发不了版）
- 一键备份 / 从备份恢复（现在只有 `catalog.json` 可读导出，不是完整备份）
- 迁移导入：Eagle `.library`、Pixcall、普通文件夹（决定能不能从竞品手里抢人）

## 7. 顺序建议

1. **先证明方法二**：几乎不用写代码，用 3000 张真实素材跑一遍，把「全量扫描的读盘成本」量出来 ——
   无感交互的前提是它自己别卡，这条不成立后面都白搭。
2. **补方法一的缺口**：位置落点（§2.1 那张表）、文件夹层级、`Ctrl+V`。
3. **补删除闭环四项**（§5）：内容修改原地更新 / 彻底删除 / 磁盘删除项的重新指认 / 目录级汇总 —— 与采集同批，
   因为都动 `file_reconcile`，晚做就要改两遍。
4. **托盘**（方法三），顺带把单实例与关闭到托盘做掉。
5. **出去三项**（拖出、复制、导出）。
6. **信得过四项**。

## 8. 已定决策（2026-10-29）

| # | 决定 | 连带要求 |
| --- | --- | --- |
| 1 | 拖到窗口的落点取**当前导航位置**；文件夹在任何位置都**保留层级**，不摊平 | 工作区要知道"我现在在哪个收藏集"，网格/画布/无限三视图共用这一个上下文；导入要能接收目录层级（现在的拖放只吃 `File`，拿不到层级） |
| 2 | 托盘**默认常驻** | 关闭进托盘；必须另给显式「退出」（否则用户只能杀进程）；单实例一起做 |
| 3 | 批量拷贝**无感** | 不设计"暂停核对"开关；反过来要求扫描更省、更安静（增量 + 降频 + 让出 IO），并把错误收敛到文件核对面板而不是弹窗 |

**2026-10-29 更正**：先前记录的"全部素材里摊平"是口误。规则已统一为 **文件夹永不摊平**，
所以 §2.1 只剩一个变量 —— 你在哪儿。这也让实现变简单：不需要"按位置决定摊平与否"的分支，
所有拖入都走同一条"建目录 + 保留层级"的路径。

## 9. 明确不做（本阶段）

- 云同步、账号体系、协作、分享链接（属于 H3，见 §10）
- 浏览器扩展（入口价值高，但依赖本地回环与 token 设计，单独一轮）
- 移动端采集

## 11. 主窗口采集子阶段交付（2026-10-29）

- 主区域按当前导航位置接收；查询条件回落收件箱，侧栏明确收藏集优先。回收站内容区域拒绝，
  打开的详情/管理面板阻止后台导入，编辑框粘贴不穿透。
- 文件夹保留顶层、子目录和空目录，普通隐藏文件保留。同名顶层目录自动加序号，文件继续不可覆盖发布，
  来源不删除。库嵌套、来源/目标包含、不可用目录与失效会话有后端保护。
- Windows 文件粘贴与拖放共用路径准备和导入。未做截图位图粘贴、托盘或导出。
- 失败进入文件问题面板；可按失败文件重试，沿用原目标，不重新复制整棵目录。
- 61 项原生测试、2 项采集规则、12 组共享原生联调、3 组真实 Tauri 检查，报告见 ADR 0009。
  真实宿主使用生产 IPC；拖放事件与联调中的剪贴板路径为受控注入，未替用户操作系统剪贴板。
- 3000 个合成普通文件准备清单约 132ms；不是 3000 张真实图片的完整导入成绩。
  §7 方法二的真实素材/峰值内存/响应性验收仍未完成。
